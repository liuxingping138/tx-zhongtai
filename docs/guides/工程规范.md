# 工程规范

本规范回答三件事：服务怎么划分、代码写成什么样、靠什么自动检查。日常约定（Excel 线程池、
筛选定义、ORM 中文 comment、提交信息格式等）已在 [`CLAUDE.md`](../../CLAUDE.md)，这里不重复，只引用。

原则：**能用工具拦的一律进 `make check`，不靠人记。** 工具拦不了的（命名是否达意、模块边界是否合理）
放进评审清单。

## 已定决策（2026-10-09）

| # | 事项 | 决定 |
| --- | --- | --- |
| A | `policy-service` 内部按领域分包，暂不拆服务 | 分成 `policy/`、`crawler/`、`scheduler/` 三个子包（已完成，见 2.4），边界用 import-linter 约束；以后某部分需要独立部署或伸缩再拆成服务 |
| B | 任务调度的归属 | 现阶段留在 `policy-service` 的 `scheduler/` 子包；客户、招投标出现定时任务时再评估是否独立成调度服务 |
| C | 跨服务引用规则 | 只存对方 ID + 少量展示字段快照；写入时调对方只读接口校验；对方变更经 Outbox 事件通知后更新快照。不跨库查询、不做分布式事务 |
| D | 各项数值门槛 | 复杂度 ≤ 10、函数参数 ≤ 6、覆盖率按现状基线只升不降（见第 4、5 节） |
| E | 整改节奏 | 「棘轮」：先登记存量问题、新代码零新增，存量按模块分批修，不做一次性大改 |

## 2. 服务划分

### 2.1 划分原则

- 按**业务能力**划服务，不按技术层划分（不建「数据库服务」「Excel 服务」）。
- **每服务一库**，库账号只授权本库。服务间不直连对方的库，也不共享表。
- 公共**技术能力**下沉到 `packages/platform-common`，公共**业务数据**留在拥有它的服务（如码表归 codebook）。
- 新建服务的门槛：有独立的数据归属，并且满足以下任一条——独立的发布节奏、独立的伸缩需求、独立的团队。
  只是代码多了，先在服务内分包。

### 2.2 现有服务与职责

| 服务 | 拥有的数据 | 对外能力 | 依赖 |
| --- | --- | --- | --- |
| iam-service | 用户、角色、授权、会话、菜单 | 登录与会话、RBAC 管理、内部授权判定 | audit（Outbox） |
| audit-service | 审计事件 | 写入（内部）、查询、到期清理 | iam（授权） |
| policy-service | 信源、基础标签、解读；爬虫监测快照；调度配置与执行记录 | 政策三表 CRUD/导入导出、爬虫监测只读统计、任务调度 | iam、audit；外部爬虫 MySQL（只读） |
| codebook-service | 政策类型、行业场景、省市区编码 | 码表 CRUD/导入导出 | iam、audit |
| customer / tender | —（占位） | — | — |

`policy-service` 内部边界见决策 A、B。

### 2.3 服务间通信

| 场景 | 方式 | 规则 |
| --- | --- | --- |
| 授权判定 | 同步 HTTP：`AuthzClient` → iam `/internal/v1/authorize` | iam 不可用时返回 503，绝不放行 |
| 审计 | 异步：本服务 `*_outbox` 表 → worker 投递 audit | 与业务写同一事务；audit 按 `event_id` 去重 |
| 跨服务引用业务数据 | 见决策 C | 不跨库 JOIN，不做分布式事务 |
| 内部接口 | `/internal/*`，`X-Internal-Service` + `X-Internal-Token` | 网关不发布 `/internal/*` |

### 2.4 服务内分层

```
api/            路由、参数解析、权限依赖、响应封装      → 只依赖 application（及 schemas）
application/    用例编排、事务边界、审计入队          → 依赖 repositories、domain
repositories/   SQLAlchemy 查询                     → 依赖 domain
domain/         模型、字段清单、纯业务规则            → 不依赖上面任何一层
core/           配置、数据库、日志等基础设施
cli/、worker/   入口，地位等同 api
```

- api 层不写查询、不直接调 repositories；注入 `AsyncSession` 只为传给 application。
- 依赖方向用 **import-linter** 写成契约，进 `make check`。
- 一个服务里有多个领域时按领域分包，每个领域内部仍是上面四层。政策服务的布局：

  ```
  app/policy/     信源、基础标签、解读
  app/crawler/    爬虫监测 v1、v2 与同步逻辑
  app/scheduler/  任务调度
  app/common/     各领域共用：审计入队、鉴权依赖、Outbox 表
  app/models.py   汇总全部表，供 Alembic 注册元数据
  ```

  政策与爬虫互不依赖；调度只经爬虫的 application 触发同步；common、core 不依赖任何领域。

## 3. API 规范

- 路径 `/api/v1/<服务>/<资源复数>`，资源名与动作名用 kebab-case。增删改查用 HTTP 方法表达
  （`POST` 新建、`PATCH` 部分更新、`PUT` 整体替换如 `/roles/{id}/grants`、`DELETE` 删除）；
  不能映射成增删改查的动作用 `POST /<资源>/{id}/<动作>`，如 `/users/{id}/reset-password`、`/roles/{id}/copy`；
  批量导入用 `POST /<资源>/import`。路径里不放 `getXxx` 这类动词式命名。
- 统一响应 `{"code", "message", "data", "request_id"}`；错误用 `platform_common.errors` 的 `ApiError` 子类，
  `code` 为大写下划线常量，`message` 为面向用户的中文。
- 列表：`page` / `page_size` 分页，筛选参数多值重复提交（`a=1&a=2`），未知筛选字段返回 422（见 `CLAUDE.md`）。
- 每个路由必须声明 `@classified(SecurityClass.*)`；受保护路由挂 `require_*_permission`，导出动作标 `GrantLevel.EXPORT`。
- 破坏性变更走新版本前缀，不在 v1 上改字段含义；OpenAPI 由 `make export-openapi` 生成，`make check` 比对。

## 4. Python 规范

### 4.1 自动检查（进 `make check`）

| 工具 | 设置 |
| --- | --- |
| ruff format | 统一格式，行宽 120 |
| ruff lint | `E W F I UP B SIM RET C4 C90 N S DTZ ASYNC PERF PL RUF T20`；`max-complexity = 10`；`max-args = 6` |
| ruff 例外 | `**/api/*` 忽略 `B008`、参数个数（FastAPI 依赖注入与查询参数）；`**/models.py` 忽略 `RUF012`；`tests/**` 忽略断言、魔法数字等；`cli/**` 允许 `T20`。完整清单与原因见根目录 `ruff.toml` |
| mypy | `strict = true`；第三方无类型库用 `[[tool.mypy.overrides]]` 单独放宽，不全局 `ignore_missing_imports` |
| import-linter | 第 2.4 节的分层契约 |
| pytest-cov | 各包 `[tool.coverage.report] fail_under` 以实测值取整为基线、精度 2 位，只升不降（见决策 D） |

`DTZ` 专门拦无时区的 `datetime.now()`：本项目时间一律经 `platform_common.clock`，按北京时间格式化。

### 4.2 写法约定

- **命名**：标识符用英文，见名知意；布尔值用 `is_` / `has_` / `can_` 前缀；不用拼音、不用单字母（循环下标除外）。
- **函数**：做一件事；超过 6 个参数改为传数据对象（`dataclass` 或 Pydantic 模型）；
  逻辑超过约 50 行或嵌套超过 3 层就拆分。拆分以「拆出来的部分能独立命名、独立测试」为准，不为凑行数拆。
- **模块**：单文件超过 400 行要在评审时说明理由；一个文件只放一个主题。
- **类型**：公开函数完整注解；不用 `Any` 逃避类型，确实需要时注释原因。
- **错误处理**：不写裸 `except:`；只捕获能处理的异常；依赖失败映射为 503，不吞掉；
  不用异常做正常流程控制。
- **注释**：写「为什么」，不复述代码；中文；对外函数写 docstring。
- **常量**：业务含义的数值（天数、上限、状态码）定义成具名常量或配置项，不写魔法数字。
- **安全**：口令、令牌不进日志（日志脱敏键见 `platform_common`）；哈希只用于去重时显式 `usedforsecurity=False`；
  SQL 一律参数化，禁止拼接用户输入。
- **例外**：确需违反规则时用行内 `# noqa: <规则>  <原因>` 或 `# type: ignore[<码>]  <原因>`，
  不写原因的忽略不予通过。

## 5. 前端规范（Vue 3 + TypeScript）

### 5.1 自动检查

| 工具 | 设置 |
| --- | --- |
| vue-tsc | `strict`、`noUnusedLocals`、`noUnusedParameters`、`noUncheckedIndexedAccess`（下标访问可能取不到值） |
| ESLint | `typescript-eslint` 的 `recommendedTypeChecked` + `eslint-plugin-vue` 的 `flat/recommended`；`no-explicit-any`、`no-floating-promises` 设为 error。`.vue` 文件关闭 `no-unsafe-*`：typescript-eslint 没有 Vue 语言服务，解析不了 SFC 组件类型，这部分由 vue-tsc 负责 |
| vitest | composables、utils、权限与路由守卫逻辑必须有单测 |
| Playwright | 关键流程 e2e，在服务器 P6 上跑（`scripts/p6-on-server.sh`） |

### 5.2 写法约定

- 遵循 Vue 官方风格指南 A、B 级规则；组件文件 PascalCase；`<script setup lang="ts">`。
- **单文件组件超过 400 行**要拆：状态与请求逻辑抽到 `composables/`，可复用的视图块抽成子组件。
  列表页优先复用 `ListPage` / `FilterBar` / `BusinessTable` 等（见 [UI 开发规范](UI开发规范.md)）。
- 请求一律走 `api/` 下的封装和 `http`，下载用 `downloadFile`，不用裸 `fetch`。
- 组件间通信：props / emits；跨页面状态用 Pinia；不用全局事件总线。
- 视觉值用 `theme.css` 变量，不写死颜色；交互规则以 `DESIGN.md`、`UX-CONTRACT.md` 为准。

## 6. 测试

- 分层：单测（纯逻辑、仓储用测试库或替身）为主，P6 集成测试覆盖跨服务链路，e2e 覆盖关键用户流程。
- 每个缺陷修复带一个能复现该缺陷的测试。
- 测试名写清「场景 + 期望」；一个测试只验证一件事。
- 不对真实业务库（8091）跑写操作测试。

## 7. 评审清单

提交前自查，评审时逐项过：

- [ ] `make check`、`make test-unit` 通过；改了跨服务链路或关键流程的，跑过 `scripts/p6-on-server.sh`
- [ ] 分层与服务边界没有越界；新增的跨服务依赖符合第 2.3 节
- [ ] 新增路由有安全分级和权限依赖；导出标了 EXPORT 档
- [ ] 新增表和列有中文 comment；迁移不 import 运行时 model
- [ ] 没有新增 `noqa` / `type: ignore`，或都写了原因
- [ ] 文档里对应的现状描述已同步（文档只写现行做法）

## 8. 落地顺序

1. **质量门**：按第 4.1、5.1 节改 `pyproject.toml`、`eslint.config`、`Makefile`；存量问题登记为基线
   （ruff 按文件的忽略清单、import-linter 的 ignore_imports、覆盖率 fail_under），新代码零新增。
2. **存量整改**，按模块分批，每批一个提交：
   继续拆分超长文件、补前端组合函数和 iam 的单测，按第 9 节逐项推进。
3. 每完成一批，删除下一节对应的差距条目，并缩小基线。
