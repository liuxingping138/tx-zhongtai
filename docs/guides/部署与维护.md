### 开发与发布

在 Mac 上用 Cursor 或 Claude Code 改代码。改完提交并推送到 GitLab：`git@103.43.186.116:development/tx-zhongtai.git`（网页 `http://103.43.186.116:8011`）。Mac 访问这个地址走本机代理，可以推送。

服务器访问不到 GitLab 的 22 和 8011，不要在服务器上 `git pull`。发布时从 Mac 把源码同步过去，再在服务器上构建。本机是 Apple 芯片，服务器是 x86，不要把本机镜像拷过去。

在 Mac 的仓库根目录执行。不要加 `--delete`，否则会把服务器上的 `.env` 和密钥目录删掉。

### 发布一次改动

```bash
rsync -az -e "ssh -i ~/.ssh/tx-zhongtai-deploy -o IdentitiesOnly=yes" \
  --exclude '.git/' \
  --exclude 'node_modules/' \
  --exclude '.venv/' \
  --exclude '__pycache__/' \
  --exclude '.mypy_cache/' \
  --exclude 'frontend/dist/' \
  --exclude '.env' \
  --exclude 'deploy/secrets/' \
  ./ txkj@1.119.196.77:/home/txkj/tx-zhongtai/
```

然后在服务器上按改动范围重建。前端改了必须带 `frontend`，只刷新页面不会变。政策服务和 `policy-worker` 共用同一个 Dockerfile，改了政策代码两个都要重建。

```bash
$DC up -d --build --no-deps frontend
$DC up -d --build policy-service policy-worker
```

多个服务一起 `up --build` 时，曾出现某一个 `uv sync` 一直不结束、整次构建卡住。卡住就停掉这次构建，改成一次只构建一个服务。`policy-worker` 可以在 `policy-service` 构建成功后执行 `sudo docker tag tx-zhongtai-policy-service:latest tx-zhongtai-policy-worker:latest`，再 `$DC up -d --no-build policy-worker`。

有表结构变更时，在新容器里迁移。四个库都迁过，不要再从本机导库覆盖。

```bash
$DC exec -T iam-service .venv/bin/alembic upgrade head
$DC exec -T audit-service .venv/bin/alembic upgrade head
$DC exec -T codebook-service .venv/bin/alembic upgrade head
$DC exec -T policy-service .venv/bin/alembic upgrade head
```

菜单或权限资源有变时再执行：

```bash
$DC exec -T iam-service .venv/bin/python -m app.cli.seed
```

发布后在服务器上核对：

```bash
curl -sS -o /dev/null -w "home %{http_code}\n" http://127.0.0.1:8091/
curl -sS -o /dev/null -w "csrf %{http_code}\n" http://127.0.0.1:8091/api/v1/auth/csrf
```

首页应为 200，csrf 应为 200。浏览器打开 `http://1.119.196.77:8091`，用原来的账号登录。JWT 密钥在服务器上单独生成，旧会话无效，需要重新登录。

### 停和起

停服务且保留数据：`$DC down`。不要加 `-v`，那会删掉已迁过来的业务库。

再次启动：`$DC up -d`。只有代码变了才加 `--build`。

## 备份与恢复

备份覆盖四个服务库：`iam` / `audit` / `policy` / `codebook`。每个库一份 `<服务>.dump` 加一份记录库名的 `<服务>.dbname`。

脚本只允许库名匹配 `*_p6_db` / `*_itest` / `*_test`，拒绝开发库（`iam_db` / `audit_db` / `policy_db` / `codebook_db`），并要求 `RESTORE_CONFIRM` 等于目标库名。

```bash
make p6-backup
RESTORE_CONFIRM=iam_p6_db make p6-restore BACKUP=deploy/backups/<stamp>
```

恢复要求备份目录四个库齐全，缺任何一个直接拒绝——否则会恢复出「框架库回到备份点、业务库还是现场数据」的混合状态。2026-09 之前的备份只有 `iam` / `audit`，不能用新脚本恢复。

`pg_restore --no-owner` 后表属主是超级用户，脚本会把四个应用账号和审计清理账号的权限补回去。生产环境应把同一套 `pg_dump`/`pg_restore` 接到独立备份存储，并先在测试库演练。Redis 丢失不影响已落库的授权。

| 观察点 | 怎么看 | 建议告警 |
| --- | --- | --- |

## 已知限制

- 单机 Compose 不是高可用。
- 表属主账号在 PostgreSQL 中可能仍显示部分属主级权限（如 TRUNCATE），应用连接未使用删除/更新历史审计。
- Playwright 与集成测试只打隔离栈，不清开发库。

## 网关响应压缩

`deploy/gateway/dynamic.yml` 的 `compress` 中间件挂在全部路由上。
JSON 与前端资源都是高压缩比文本，实测：

| 响应 | 未压缩 | gzip | 节省 |
| --- | --- | --- | --- |
| `/policy/sources/options` | 962KB | 134KB | 86% |
| `/codebook/scenarios/options` | 107KB | 21KB | 80% |
| 列表首屏 20 条 | 12KB | 2.5KB | 79% |
| 前端主包 | 1.14MB | 392KB | 66% |

xlsx、zip、图片等本身已压缩的类型在 `excludedContentTypes` 里排除，
再压一次没有收益，只会白白消耗两端 CPU。Traefik 默认只压缩超过 1KB 的响应。

## 会话与刷新令牌清理

`iam_sessions` 和 `iam_refresh_tokens` 只增不减：每次登录写一行会话，
每次刷新写一行令牌。没有清理任务时会一直涨（开发环境几天就 300+ 行）。

```bash
make iam-session-cleanup
```

- 只删**已过期**或**已撤销**、且再往前推 `IAM_SESSION_RETENTION_DAYS`
  （默认 30 天）的记录；在用会话和最近失效的会话都不动。
- 先删令牌再删会话：`iam_refresh_tokens.session_id` 是
  ON DELETE RESTRICT，顺序反了会被外键挡住。
- 建议按月执行；执行后日志会打印删除数与剩余数，便于观察增长趋势。

在一次性探测库上用受控夹具验证过：40 天前过期、40 天前撤销的两个会话
及其 4 个令牌被删除；在用会话和 2 天前刚过期的会话保留；无孤儿令牌。

## 客户端 IP 的信任前提

登录限流和审计留痕里的来源 IP 取自 `X-Forwarded-For` 的第一段，
由网关写入。Traefik 默认丢弃客户端自带的 `X-Forwarded-*` 再重写
（已实测：伪造 `X-Forwarded-For: 203.0.113.99` 不会进入服务）。

由此带来两条部署约束：

- 各服务端口（8001–8004）**不得**直接对外暴露，只能经网关访问。
- 不要在 Traefik 前面再加一层不做同样清洗的代理。

任一条被打破，攻击者就能自行构造该头，绕过按 IP 的登录限流，
并在审计日志里伪造来源 IP。按账号维度的限流不受影响，仍然生效。
