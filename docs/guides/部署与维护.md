### 发布一次改动

在 Mac 的仓库根目录执行：

```bash
bash scripts/sync-to-server.sh
```

脚本读本机 `.env` 的 `DEPLOY_HOST` / `DEPLOY_USER`，排除列表只在脚本里维护一份（部署和服务器上跑 P6 共用）。
工作区有没提交的改动时脚本拒绝同步：推过去的代码下一次 `up --build` 就进了生产，网关动态配置更是立刻生效。先提交再发布；
只想在服务器上跑 P6 用 `scripts/p6-on-server.sh`，它同步到单独的目录，允许没提交。

脚本带 `--delete`：本地删掉的文件，服务器上也会删掉，不会残留下来被打进镜像，e2e 也不会跑到已删除的用例。
被排除的路径在服务器上不会被删，服务器独有的东西都靠排除列表保护：`.env`、`deploy/secrets/`（JWT、P6 密钥、TLS 证书）、
`deploy/compose/.p6.*`、`frontend/e2e/.admin-password`、`deploy/backups/`、根目录的 `.env.*`（`.env.bak` 一类手工备份）和 `*.bak`，以及 `node_modules`、`.venv` 等依赖与缓存。
**在服务器上新建本地没有的文件或目录前，先把它加进脚本的排除列表**，否则下次同步就会被删掉。

额外的 rsync 参数可以跟在后面。改了排除列表，或者不确定会删什么时，先用 `-n -i` 预演，看 `*deleting` 开头的行：

```bash
bash scripts/sync-to-server.sh -n -i | grep '^\*deleting'
```

然后在服务器上按改动范围重建。前端改了必须带 `frontend`，只刷新页面不会变。政策服务和 `policy-worker`、
IAM 和 `iam-worker`、AI提问的 `ai-service` 和 `ai-worker` 各共用一个 Dockerfile，改了代码两个都要重建（第二个全部命中缓存，几秒完成）。改了
`packages/platform-common` 就重建全部 Python 服务。

```bash
$DC up -d --build --no-deps frontend
$DC up -d --build policy-service policy-worker
$DC up -d --build ai-service ai-worker
$DC up -d --build iam-service iam-worker audit-service audit-worker codebook-service policy-service policy-worker ai-service ai-worker tender-service thinktank-service frontend  # 全部
```

构建走 BuildKit，多个服务并行。只改代码时全部重建约 1 分钟；改了依赖（锁文件变化）也只下载新增的包。
做到这点靠两件事，改 Dockerfile 时不要破坏：

- 第三方依赖层只拷 `pyproject.toml` 和 `uv.lock`，并用 `--no-emit-package platform-common` 跳过公共包，
  源码在依赖层之后才拷入；`uv` / `pnpm` 的下载缓存用 `RUN --mount=type=cache` 挂载。
- `uv.lock` 只锁版本和哈希，不锁下载源。镜像里先 `uv export` 出带哈希的版本清单，再 `uv pip install` 从构建参数 `PYPI_INDEX`
  指定的源装（默认腾讯镜像；阿里云在这台机器上只有 190KB/s）。换源不用动锁文件：
  `$DC build --build-arg PYPI_INDEX=https://repo.huaweicloud.com/repository/pypi/simple`。不要改回 `uv sync --frozen`，它只认锁文件里记的地址。
  uv 本身也用 pip 从这个源装，不去 ghcr.io 拉镜像。
- 不要 `chown -R /srv`：它会把整个 `.venv` 复制一遍，单这一步要 5 分钟。`/srv` 保持 root 所有，appuser 只读即可。

服务器的 buildx 插件 v0.19.3（`/usr/local/lib/docker/cli-plugins/docker-buildx`）和 docker-compose v5.0.2 都是手工装的独立程序，
核对过官方 SHA256：docker-compose 要求 buildx ≥ 0.17，CentOS 7 的 docker-ce 源里没有这么新的。升级照同样方法，
在 Mac 下载、核对 SHA256 后传上去。没有可用的 buildx 时 `docker-compose build` 会直接报错，不会退回旧构建器。

刚 `stop` 过的服务要重新拉起时用 `$DC up -d --no-deps --force-recreate <服务>`：服务器上这版 docker-compose
偶尔在 stop 之后读到过时状态，`start` 或普通 `up -d` 返回成功却没有真正启动容器。

有表结构变更时，在新容器里迁移。不要从本机导库覆盖服务器上的库。

审计库归超级用户所有（应用账号对 `audit_events` 只有查和插，改不了表结构），审计服务的迁移用超级用户跑，
跑完由 `deploy/compose/scripts/secure-audit-db.sh` 重新收紧权限，两步都在 `make SERVER=1 migrate-audit` 里：

```bash
make SERVER=1 migrate   # 推荐：统一执行全库 Alembic 迁移

# 如需按服务单独执行：
$DC exec -T iam-service .venv/bin/alembic upgrade head
make SERVER=1 migrate-audit
$DC exec -T codebook-service .venv/bin/alembic upgrade head
$DC exec -T policy-service .venv/bin/alembic upgrade head
$DC exec -T ai-service .venv/bin/alembic upgrade head
$DC exec -T thinktank-service .venv/bin/alembic upgrade head
```

菜单或权限资源有变时再执行：

```bash
$DC exec -T iam-service .venv/bin/python -m app.cli.seed
```

iam-service 把资源和动作目录在进程里缓存 60 秒：新加的模块 seed 完就能用，下线、取消发布的最多一分钟后才在鉴权里生效，
要立即生效就重建容器：`$DC up -d --no-deps --force-recreate iam-service`。

发布后在 Mac 上核对（服务器自己访问自己的公网地址不一定通）：

```bash
curl -sS -o /dev/null -w "home %{http_code}\n" https://36.134.128.137:8443/
curl -sS -o /dev/null -w "csrf %{http_code}\n" https://36.134.128.137:8443/api/v1/auth/csrf
```

首页和 csrf 都应为 200。改了前端的，再用浏览器打开 `https://36.134.128.137:8443` 看一眼改动的页面。

## 在服务器上跑隔离验收（P6）

集成测试和 e2e 默认在这台服务器上跑，Mac 不需要开 Docker。在 Mac 仓库根目录执行：

```bash
bash scripts/p6-on-server.sh               # 同步源码 → 集成 + e2e → p6-down
bash scripts/p6-on-server.sh integration   # 只跑集成（含任务调度、AI提问集成测试）
```

隔离方式：源码同步到单独的 `/data/tx-zhongtai-p6`（`P6_DEPLOY_DIR` 可改），不碰生产的 `/data/tx-zhongtai`，所以没提交的改动也能先跑 P6；
第一次在新目录跑时会生成自己的 `.p6.env` 和 `deploy/secrets/jwt-p6`。项目名 `tx-zhongtai-p6`，独立的卷、网络和 `*_p6_db` 库；网关只绑 `127.0.0.1:8090`，
Postgres 绑 `127.0.0.1:5434`，不对外暴露，也不碰 8091 的业务栈。脚本无论成败都会 `p6-down`
删掉隔离卷，并清掉 `.p6.runtime`、`.admin-password`。失败时脚本会先打印各服务状态和 iam、网关的最近日志（`make P6_SERVER=1 p6-logs`），再清理现场。

服务器上的差异由 `P6_SERVER=1` 切换：compose 用独立的 `docker-compose`；e2e 在 Playwright 官方镜像里跑（`scripts/e2e-docker.sh`，
镜像版本跟 `@playwright/test` 一致），服务器不用装 Node 和浏览器。这个镜像在 mcr.microsoft.com，Docker Hub 加速管不到，
直连要拉半个多小时：升级 `@playwright/test` 后先在服务器上 `docker pull m.daocloud.io/mcr.microsoft.com/playwright:v<版本>-noble`，
再 `docker tag` 成 `mcr.microsoft.com/playwright:v<版本>-noble`（2.5GB 约 7 分钟）。P6 JWT 密钥用 openssl 生成到
`deploy/secrets/jwt-p6`，root 生成后把属主改成 1000，容器里 uid 1000 的 appuser 才能读。

每次都会重新构建 P6 镜像（`p6-up` 带 `--build`），首次还要拉 Playwright 镜像、装 npm 依赖，会慢一些。

## 备份与恢复

备份覆盖五个服务库：`iam` / `audit` / `policy` / `codebook` / `ai`。每个库一份 `<服务>.dump` 加一份记录库名的 `<服务>.dbname`。

脚本只允许库名匹配 `*_p6_db` / `*_itest` / `*_test`，拒绝开发库（`iam_db` / `audit_db` / `policy_db` / `codebook_db` / `ai_db`），并要求 `RESTORE_CONFIRM` 等于目标库名。

```bash
make p6-backup
RESTORE_CONFIRM=iam_p6_db make p6-restore BACKUP=deploy/backups/<stamp>
```

恢复要求备份目录六个库齐全，缺任何一个直接拒绝——否则会恢复出「框架库回到备份点、业务库还是现场数据」的混合状态。

`pg_restore --no-owner` 之后，脚本会把当前库 public 里的表、序列和函数属主改回应用账号，再补 GRANT。只做 GRANT 时，后面的迁移仍可能因为不是属主而失败。恢复是否成功，要看到应用账号能执行下一次迁移，不能只数行数。

业务库不走上面的隔离恢复入口。只读导出六个库，并把 AI提问、智库的附件卷分别打包压缩成 `ai-files.tar.gz`、`thinktank-files.tar.gz`（早期的备份是不压缩的 `ai-files.tar`，恢复时去掉 `z`）。默认写在 `/data/tx-zhongtai-backups`，分区剩余空间少于 `BACKUP_MIN_FREE_GB`（默认 10G）就不备份；批量任务正在写的文件不会让备份失败：

```bash
CONFIRM_BUSINESS_BACKUP=yes BACKUP_COMPOSE="$DC" BACKUP_ENV_FILE=.env bash scripts/backup_business.sh
```

备份默认写到运行用户家目录的 `tx-zhongtai-backups/<时间>/`。这个脚本不会把备份灌回 `iam_db` 等业务库。要演练恢复，先导入临时库或隔离库，确认应用账号能迁移，再由人工决定是否切换。现有隔离库白名单保持不变。

AI提问附件要和 `ai` 库回到同一备份点，切换时先停 `ai-worker`，再灌回卷里：

```bash
$DC stop ai-worker
$DC exec -T ai-service tar -C /data/ai -xzf - < <备份目录>/ai-files.tar.gz
$DC start ai-worker
```

智库附件要和 `thinktank` 库回到同一备份点（智库没有 worker，服务留着执行解包）：

```bash
$DC exec -T thinktank-service tar -C /data/thinktank -xzf - < <备份目录>/thinktank-files.tar.gz
```

隔离恢复（`make p6-restore BACKUP=...`）时备份目录里有这两个包，`scripts/restore.sh` 会按上面的做法一起灌回，
`scripts/verify_restore_p6.py` 再逐个核对包里的文件都回到了卷里；`scripts/backup.sh` 只备库，没有附件包，跳过这一步。

Redis 丢失不影响已经落库的授权。会话限流计数会清空。

## 指标与告警

| 观察点 | 怎么看 | 建议告警 |
| --- | --- | --- |
| 服务存活 | 容器内 `/health/live`、`/health/ready`（网关不公开） | 连续失败 |

| Outbox 积压 | IAM `GET /internal/v1/outbox/metrics`（内部凭据）或 Worker 日志 `outbox_metrics` | `dead_count>0`；`oldest_unfinished_age_seconds>600` |
| 登录限流 | 登录 429 / Redis 宕机 503 | 持续 503 |
| 网关错误率 | Traefik 访问日志中 5xx | 按部署要求 |

生产关闭 OpenAPI 与文档页：设置全局 `ENVIRONMENT=production`，或单独设置 `IAM_ENVIRONMENT` / `AUDIT_ENVIRONMENT` / `CODEBOOK_ENVIRONMENT` / `POLICY_ENVIRONMENT` / `AI_ENVIRONMENT`，单独设置的覆盖全局值。演示密钥在 production 下会拒绝启动。

## HTTPS

`deploy/gateway/dynamic.https.yml` 里 `secure-headers` 中间件给所有路由加 HSTS（一年）、`nosniff`、禁止被 iframe、referrer 策略；TLS 最低 1.2。改了动态配置文件同步上去即生效，Traefik 在 watch 它。

服务器没有域名，按访问地址申请 Let's Encrypt 的短期 IP 证书，有效期约 6 天，必须自动续期。宿主机 443 被同机其他站点占用，网关 HTTPS 用 8443。
续期脚本用 certbot 的 standalone 模式，校验那几秒临时监听宿主机 80，所以 80 要一直空着。

```bash
# 在服务器上。PUBLIC_IP 填浏览器地址栏里的主机地址；/etc/tx-zhongtai-acme.env 里也只写了这一项。
PUBLIC_IP=36.134.128.137 bash scripts/renew_ip_cert.sh
```

证书写到 `deploy/secrets/tls/`，该目录不进 Git。然后在原有 Compose 上叠加 HTTPS 文件。8091 仍接收 HTTP，并跳到 `https://<地址>`。叠加之后刷新 Cookie 带 Secure。

```bash
DC="docker-compose -f deploy/compose/docker-compose.yml -f deploy/compose/docker-compose.https.yml --env-file .env"
$DC up -d gateway iam-service
```

续期由 `tx-zhongtai-cert-renew.timer` 每天两次调用同一个脚本。脚本更新证书并原子替换动态配置，触发 Traefik 重新加载。证书文件还没放好时不要叠加 `docker-compose.https.yml`，否则网关起不来。

宿主机没有启用 firewalld，端口由云安全组控制，现已放行 80、8443、8091、5433。

## 已知限制

- 单机 Compose 不是高可用。
- 表属主账号在 PostgreSQL 中可能仍显示部分属主级权限（如 TRUNCATE），应用连接未使用删除/更新历史审计。
- Playwright 与集成测试只打隔离栈，不清开发库。

## 网关响应压缩

`deploy/gateway/dynamic.yml` 的 `compress` 中间件挂在除 `/api/v1/ai/stream` 流式接口外的全部路由上。
JSON 与前端资源都是高压缩比文本，实测：

| 响应 | 未压缩 | gzip | 节省 |
| --- | --- | --- | --- |
| `/policy/sources/options` | 962KB | 134KB | 86% |
| `/codebook/scenarios/options` | 107KB | 21KB | 80% |
| 列表首屏 20 条 | 12KB | 2.5KB | 79% |
| 前端主包 | 1.14MB | 392KB | 66% |

xlsx、zip、图片等本身已压缩的类型在 `excludedContentTypes` 里排除，
再压一次没有收益，只会白白消耗两端 CPU。Traefik 默认只压缩超过 1KB 的响应。

## 会话与刷新令牌清理

`iam_sessions` 和 `iam_refresh_tokens` 只增不减：每次登录写一行会话，
每次刷新写一行令牌。没有清理任务时会一直涨（开发环境几天就 300+ 行）。

```bash
make iam-session-cleanup
```

- 只删**已过期**或**已撤销**、且再往前推 `IAM_SESSION_RETENTION_DAYS`
  （默认 30 天）的记录；在用会话和最近失效的会话都不动。
- 先删令牌再删会话：`iam_refresh_tokens.session_id` 是
  ON DELETE RESTRICT，顺序反了会被外键挡住。
- 建议按月执行；执行后日志会打印删除数与剩余数，便于观察增长趋势。

## 客户端 IP 的信任前提

登录限流和审计留痕里的来源 IP 取自 `X-Forwarded-For` 的第一段，
由网关写入。Traefik 默认丢弃客户端自带的 `X-Forwarded-*` 再重写
（已实测：伪造 `X-Forwarded-For: 203.0.113.99` 不会进入服务）。

由此带来两条部署约束：

- 各服务端口（8001–8006）**不得**直接对外暴露，只能经网关访问。
- 不要在 Traefik 前面再加一层不做同样清洗的代理。

任一条被打破，攻击者就能自行构造该头，绕过按 IP 的登录限流，
并在审计日志里伪造来源 IP。按账号维度的限流不受影响，仍然生效。

## HTTPS 端口、请求体上限与备份约定

- HTTPS 使用宿主机 **8443**（443 被同机其他站点占用），8091 重定向到 8443。HTTPS overlay 固定映射 `8443:8443`，修改端口必须同时修改 `traefik.https.yml` 的静态入口和跳转目标，不能只改宿主机映射。
- IP 证书使用 Certbot 5.4.0 容器的 standalone 模式（宿主机 80 空着），每天两次运行 `scripts/renew_ip_cert.sh`。脚本将证书写入 TLS 目录并原子替换动态配置，触发网关重载。依据：[Let's Encrypt 的 IP 证书说明](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)。发布涉及网关时验证证书 IP SAN、有效期、HTTPS 页面/CSRF、8091 的 Location；续期用 `certbot renew --dry-run` 在 staging 验证。
- 网关总请求上限为 21233664 字节（20MiB 加 256KiB multipart 开销）。服务 `IMPORT_MAX_BYTES` 若调大，需要同步调整两份 dynamic 配置；仅改服务参数不会提升公网限额。
- **当前没有定时备份、自动清理或异机备份**，也没有周期性 RPO 承诺；证书自动续期是独立的定时任务，与数据库备份无关。需要备份时手动运行 `scripts/backup_business.sh`（见上文「备份与恢复」）。恢复演练目标 RTO 2 小时。五库串行快照不承诺跨库同一时刻，需要严格共同恢复点时先停止本项目写入及 worker，再备份。
- 备份脚本先写临时目录，五库导出、附件打包和归档检查全成功后生成 SHA256SUMS/COMPLETE 并原子发布；失败返回非零，不删除旧备份。每次运行默认清理超过 14 天的完整备份，`BACKUP_ROOT` 指定目录，`BACKUP_RETENTION_DAYS` 调整保留天数。以退出码和终端输出判断成败，目录里有 COMPLETE、SHA256SUMS 校验通过才算完整恢复点。
- 异机备份（可选，未启用）：设置 `BACKUP_OFFSITE=备份用户@备份主机:/专用目录`，预先配置受限 SSH 密钥、known_hosts 和目录权限；脚本 rsync 成功才写 OFFSITE_SENT。异机目标建议保留 30 天，并在服务端设独立的保留/版本策略，不能依赖源服务器删除策略。
- 恢复演练必须在隔离实例/库执行：校验 `sha256sum -c SHA256SUMS`，将备份导入 `*_p6_db` 等允许库，恢复应用 owner，使用应用账号运行 `alembic upgrade head`、`alembic check` 和下一次临时迁移，并验证数据及登录。业务备份 `.dbname` 记录业务库名，禁止为了绕过保护直接在原恢复脚本中放宽白名单；演练应复制到独立目录，审阅目标映射后只修改该副本的 `.dbname`。
