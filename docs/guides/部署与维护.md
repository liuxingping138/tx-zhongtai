# 部署与维护

本期不执行生产上线。下面是本地运行、备份恢复和日常检查步骤。

## 本地启动

```bash
make bootstrap          # 不覆盖已有 .env
# 编辑 .env 中的密码
make dev-up
make migrate
make seed
ADMIN_PASSWORD='...' make admin-create
make smoke
```

浏览器访问 `http://localhost:8080`。停止且保留数据：`make dev-down`。

隔离验收（独立项目名、网络、卷、库，不碰开发数据）：

```bash
make p6-up
make test-integration
make test-e2e
make p6-down            # 删除隔离卷
```

## 日常命令

| 命令 | 用途 |
| --- | --- |
| `make seed` | 幂等同步资源/动作/菜单/超级管理员角色 |
| `make outbox-replay` | 重放 iam/policy/codebook 的 dead/failed Outbox；`OUTBOX_SERVICES=policy-service` 只跑一个 |
| `make audit-cleanup` | 用清理账号删除到期审计 |
| `make export-openapi` | 从本地 FastAPI 应用导出 OpenAPI 到 `docs/openapi/` |
| `make scan-scope` | 确认业务目录无源码、仓库无私钥 |

## 备份与恢复

备份覆盖四个服务库：`iam` / `audit` / `policy` / `codebook`。每个库一份 `<服务>.dump` 加一份记录库名的 `<服务>.dbname`。

脚本只允许库名匹配 `*_p6_db` / `*_itest` / `*_test`，拒绝开发库（`iam_db` / `audit_db` / `policy_db` / `codebook_db`），并要求 `RESTORE_CONFIRM` 等于目标库名。

```bash
make p6-backup
RESTORE_CONFIRM=iam_p6_db make p6-restore BACKUP=deploy/backups/<stamp>
```

恢复要求备份目录四个库齐全，缺任何一个直接拒绝——否则会恢复出「框架库回到备份点、业务库还是现场数据」的混合状态。2026-09 之前的备份只有 `iam` / `audit`，不能用新脚本恢复。

`pg_restore --no-owner` 后表属主是超级用户，脚本会把四个应用账号和审计清理账号的权限补回去。生产环境应把同一套 `pg_dump`/`pg_restore` 接到独立备份存储，并先在测试库演练。Redis 丢失不影响已落库的授权。

## 指标与告警

| 观察点 | 怎么看 | 建议告警 |
| --- | --- | --- |
| 服务存活 | 容器内 `/health/live`、`/health/ready`（网关不公开） | 连续失败 |
| 鉴权超时/不可用 | 审计查询返回 `DEPENDENCY_UNAVAILABLE` 503 | 5 分钟错误率上升 |
| Outbox 积压 | IAM `GET /internal/v1/outbox/metrics`（内部凭据）或 Worker 日志 `outbox_metrics` | `dead_count>0`；`oldest_unfinished_age_seconds>600` |
| 登录限流 | 登录 429 / Redis 宕机 503 | 持续 503 |
| 网关错误率 | Traefik 访问日志中 5xx | 按部署要求 |

生产关闭 OpenAPI 与文档页：`IAM_ENVIRONMENT=production` / `AUDIT_ENVIRONMENT=production`。

## 已知限制

- 单机 Compose 不是高可用。
- 表属主账号在 PostgreSQL 中可能仍显示部分属主级权限（如 TRUNCATE），应用连接未使用删除/更新历史审计。
- Playwright 与集成测试只打隔离栈，不清开发库。

## 网关响应压缩

`deploy/gateway/dynamic.yml` 的 `compress` 中间件挂在全部路由上。
JSON 与前端资源都是高压缩比文本，实测：

| 响应 | 未压缩 | gzip | 节省 |
| --- | --- | --- | --- |
| `/policy/sources/options` | 962KB | 134KB | 86% |
| `/codebook/scenarios/options` | 107KB | 21KB | 80% |
| 列表首屏 20 条 | 12KB | 2.5KB | 79% |
| 前端主包 | 1.14MB | 392KB | 66% |

xlsx、zip、图片等本身已压缩的类型在 `excludedContentTypes` 里排除，
再压一次没有收益，只会白白消耗两端 CPU。Traefik 默认只压缩超过 1KB 的响应。

## 会话与刷新令牌清理

`iam_sessions` 和 `iam_refresh_tokens` 只增不减：每次登录写一行会话，
每次刷新写一行令牌。没有清理任务时会一直涨（开发环境几天就 300+ 行）。

```bash
make iam-session-cleanup
```

- 只删**已过期**或**已撤销**、且再往前推 `IAM_SESSION_RETENTION_DAYS`
  （默认 30 天）的记录；在用会话和最近失效的会话都不动。
- 先删令牌再删会话：`iam_refresh_tokens.session_id` 是
  ON DELETE RESTRICT，顺序反了会被外键挡住。
- 建议按月执行；执行后日志会打印删除数与剩余数，便于观察增长趋势。

在一次性探测库上用受控夹具验证过：40 天前过期、40 天前撤销的两个会话
及其 4 个令牌被删除；在用会话和 2 天前刚过期的会话保留；无孤儿令牌。

## 客户端 IP 的信任前提

登录限流和审计留痕里的来源 IP 取自 `X-Forwarded-For` 的第一段，
由网关写入。Traefik 默认丢弃客户端自带的 `X-Forwarded-*` 再重写
（已实测：伪造 `X-Forwarded-For: 203.0.113.99` 不会进入服务）。

由此带来两条部署约束：

- 各服务端口（8001–8004）**不得**直接对外暴露，只能经网关访问。
- 不要在 Traefik 前面再加一层不做同样清洗的代理。

任一条被打破，攻击者就能自行构造该头，绕过按 IP 的登录限流，
并在审计日志里伪造来源 IP。按账号维度的限流不受影响，仍然生效。
