# 任务调度

系统管理 → 任务调度（`/system/scheduler`）。

## 范围

- 四项任务：爬虫监测增量同步（编码 `crawler`），默认每天北京时间 10:10；政策 AI 打标的三个任务：政策类型判断（`policy_ai_type`）、
  政策解读（`policy_ai_interpret`，默认 11:00）、政策市场机会（`policy_ai_opportunity`，默认 11:30），上线时都默认停用，
  先在页面「立即执行」试跑几批，确认结果再打开每日计划。
- 每日时刻、启用/停用、立即执行、执行记录和详情，在线心跳，失败原因、重试时间、源数据水位。
- 任务是代码登记的白名单，不允许页面输入 shell 命令或任意 SQL。
- 不提供计划内全量回填。任务要求已有成功水位，无水位时明确失败，管理员先按爬虫说明完成首次回填。

## 服务与数据

前端页面放在系统管理，API 在 policy-service：`/api/v1/policy/scheduled-jobs`。
IAM 资源 `system.scheduler` 属于 policy-service，READ 查看，FULL 设置和执行，无导出档。
现有角色需授予该模块权限，超级管理员经资源目录同步自动拥有权限。

policy-worker 与 policy-service 使用同一 Dockerfile/代码，独立进程运行；不依赖浏览器打开。
配置及队列持久化在政策库：`policy_scheduled_jobs`、`policy_scheduled_runs`、`policy_scheduler_heartbeat`。
每 5 秒检查到期计划，每 10 秒写心跳；超过 60 秒无心跳页面提示离线。
worker 同时连接 data 和 gateway 网络，后者用于外部爬虫库出站访问，不发布新端口。

## 执行规则

- 以 Asia/Shanghai 计算每日时刻，存储 UTC。首次迁移安排下一次每日时刻，不追溯尚未建立计划的往日。
- 已存在计划错过多天，恢复后合并为一次增量；按成功入库水位回算受影响采集日，不按漏掉几天重复排几个任务。
- worker 全局 PostgreSQL 会话锁确保仅一个进程消费；每个任务继续使用原同步锁，与手动 CLI 互斥。
- 同一任务 queued/running/retrying 最多一个；行锁与部分唯一索引同时防止手动/定时重复提交。多个任务时串行执行。
- 最多 3 次尝试（首次 + 2 次重试），重试分别等待 60 秒和 300 秒；一次尝试最长：爬虫 30 分钟、AI 打标 6 小时。
- 重启后检查原同步批次，已成功则补记完成，未完成则按重试预算继续，不无限重试。
- 停用计划取消排队和等待重试，已经执行的批次继续完成；仍可手动执行。启用后从下次计划时间开始。
- 任务完成时间和“数据更新至”不同，后者是源库入库水位。配置变更和手动触发通过 Outbox 写操作日志。
- 记录详情显示最新尝试对应同步批次；失败尝试的完整同步记录仍保留在原爬虫同步表中。
- policy-worker 停机期间不执行，恢复后按上面的合并规则补跑一次。

## 发布

在服务器上按 [部署与维护](部署与维护.md) 使用 `docker-compose` 重建。政策服务和 `policy-worker` 共用镜像，前端有路由变化时必须重建 `frontend`。先迁移再启动 worker。不要同时加宿主机 cron，也不要在多个 API 进程里再跑一套定时循环。

## 验证

单测：`services/policy-service` 目录执行 `.venv/bin/pytest -q`。
集成测试随服务器 P6 自动执行（`bash scripts/p6-on-server.sh`，由 `scripts/scheduler-integration.sh` 在 P6 的 Postgres 里
建临时库 `scheduler_test`、迁移后运行）。只允许数据库名 `scheduler_test`，禁止指向业务库。手动运行：

```sh
SCHEDULER_INTEGRATION=1 POLICY_DATABASE_URL=postgresql+asyncpg://<测试用户>:<测试密码>@127.0.0.1:<测试端口>/scheduler_test \
  .venv/bin/pytest tests/test_scheduler_integration.py -q
```

先用新镜像在空库执行 `alembic upgrade head`，再执行 `alembic check` 与集成测试。
测试覆盖：并发手动请求、定时/手动竞争、停机多天合并、停用取消、版本冲突、失败重试、重启恢复、无水位拒绝和 API 权限校验。

## 政策 AI 打标

三个独立任务，各占任务列表一行（权限同样是 `system.scheduler`：READ 看，FULL 改设置和执行）：

| 任务 | 做什么 | 取哪些政策 |
| --- | --- | --- |
| 政策类型判断 | 判断政策类型写基础标签，含信息化建设类的标「是否解读 = 是」 | 从读取进度往后读源库的新政策，读完进度前移 |
| 政策解读 | 一条政策展开成多行写政策解读列表，非新增场景到码表查编码 | 基础标签里需要解读、还没解读的 |
| 政策市场机会 | 按一级行业 + 一级场景回填到解读行 | 解读过、还没补市场机会的 |

- 每个任务的「设置」抽屉：使用的模板（只列政策类、已上线的；跑的是上线版本，之后改模板草稿不影响）、每批条数、
  正文长度（默认「全文」整篇发给模型；选「截取前 N 字」才截断）、每日费用上限；类型判断多一项起始采集日期（改了就从那天第一条重读）；最后是每日计划。
- 每批以这个任务当日剩余额度为费用上限、按低优档跑；额度用完时这批什么都不问并写明。费用到上限没轮到的政策留到下一批。
- 后两个任务按待办做，前一个没跑后一个就没有待办，不需要串起来。定时时错开时刻，让类型判断先跑。
- 列表上「今日费用 / 上限」按任务分开算；执行中在状态旁显示模型答到第几条。
- 没选模板、AI 服务明确拒绝（如模板已下线）这类设置问题直接失败不重试，执行记录写明原因；连不上、超时照常重试。
- 列表「每日计划」列直接启停；启用打标任务前会确认它每天会花钱。
- 「执行记录」抽屉每次执行一行，「结果」列写说明和花费；花费明细统一在「AI提问 → 费用账单」看，打标任务的抽屉里有「查看费用账单」直接跳过去并筛好这个任务。
  对应的批量任务在「AI提问 → 批量提问」历史里能看到逐行结果。
- 首次上线：三个任务都选好模板，类型判断的每批条数设小（如 10），依次立即执行三个任务，到「政策基础标签」「政策解读」核对，再调大条数、打开每日计划。
