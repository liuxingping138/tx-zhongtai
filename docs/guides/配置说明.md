# 配置说明

真实密钥只放在本机 `.env` 或密钥目录，不提交仓库。`.env.example` 只提供字段清单和演示值。

## 环境标识

| 值 | 用途 |
| --- | --- |
| `development` | 本地 Compose / `pnpm dev` |
| `test` | 隔离验收栈（P6） |
| `production` | 生产模板；演示密钥会被拒绝启动 |

各服务环境变量前缀：IAM 用 `IAM_`，审计用 `AUDIT_`，码表用 `CODEBOOK_`，政策用 `POLICY_`，AI提问用 `AI_`。

Compose 不会把整个 `.env` 自动送进容器。某项要生效，必须出现在 `deploy/compose/docker-compose.yml` 该服务的 `environment` 里。全局 `ENVIRONMENT` 是各服务环境的默认值；单独设置 `IAM_ENVIRONMENT` 等会覆盖它。政策 API 和 `policy-worker` 使用同一组导入、导出和爬虫阈值。

容器里只应打印白名单参数，例如：

```bash
docker-compose exec -T iam-service .venv/bin/python -c "from app.core.config import get_settings; from platform_common.public_config import dump_public_settings; print(dump_public_settings(get_settings(), 'iam'))"
```

不要打印完整环境变量。

## 必填项

| 变量 | 说明 |
| --- | --- |
| `POSTGRES_SUPERUSER` / `POSTGRES_SUPERUSER_PASSWORD` | 仅初始化脚本用，应用不使用 |
| `IAM_DB_*` / `AUDIT_DB_*` / `CODEBOOK_DB_*` / `POLICY_DB_*` / `AI_DB_*` | 各自独立库与账号 |
| `AUDIT_CLEANUP_DB_USER` / `AUDIT_CLEANUP_DB_PASSWORD` | 到期清理专用账号 |
| `IAM_INTERNAL_CALLER_SECRETS` | 调用 IAM 内部接口的服务名→密钥 |
| `IAM_AUDIT_INGEST_SECRET` | Worker 写审计的内部密钥 |
| `AUDIT_INTERNAL_CALLER_SECRETS` | 允许写审计的服务名→密钥 |
| `AUDIT_IAM_SERVICE_SECRET` | 审计查询时调 IAM 授权的密钥 |

JWT 私钥目录：`deploy/secrets/jwt`（gitignore）。`make bootstrap` / `make jwt-keys` 会生成开发密钥。

## 会话与安全默认值

- Access Token 默认 8 小时（`IAM_ACCESS_TOKEN_TTL_SECONDS`），Refresh / 会话 7 天，算法 RS256。
- 旧刷新令牌在 `IAM_REFRESH_REUSE_GRACE_SECONDS`（默认 30 秒）内可以重复成功。超过这个时间会撤销整个会话族，撤销和安全审计在返回 401 前提交。
- Refresh Cookie：`HttpOnly`，`Path=/api/v1/auth`，`SameSite=strict`。`IAM_COOKIE_SECURE` 默认 false；启用 HTTPS 叠加文件后为 true。
- 登录失败按两个维度限流，窗口都是 300 秒：同一账号 5 次（`IAM_LOGIN_MAX_FAILURES`，用户名去空格、转小写后计数），
  同一 IP 20 次（`IAM_LOGIN_MAX_FAILURES_PER_IP`，登录成功不清零）。Redis 不可用时登录返回 503。
- 审计默认保留 180 天，由 `AUDIT_RETENTION_DAYS` 调整。
- 会话/刷新令牌失效后默认再留 30 天，由 `IAM_SESSION_RETENTION_DAYS` 调整，`make iam-session-cleanup` 执行清理。
- 在线用户：最近 30 分钟内有操作的设备算在线（`IAM_ONLINE_WINDOW_SECONDS`，默认 1800）；「最近活跃」每台设备至多 60 秒写一次库
  （`IAM_SESSION_TOUCH_SECONDS`）。这两项用代码默认值，compose 没有传，要改先加进 iam-service 的 `environment`。

## 筛选项候选值

八个列表页（六张业务表、爬虫监测、操作日志）统一走同一套机制。

`GET <业务前缀>/options` 每个字段最多返回 200 个候选，超出则标 `truncated`；
前端对被截断的字段改调 `GET <业务前缀>/options/search?field=&q=`（每次最多 50 条）。

不一次性下发全部去重值：信源的网站名称有 1 万多个不同值，全量下发单次响应接近 1MB，截断又会让排序靠后的值搜不到。
上限常量在 `platform_common/options.py` 的 `PREVIEW_LIMIT` / `SEARCH_LIMIT`。

## 导入导出限制

policy-service 与 codebook-service 各自生效，环境变量前缀分别是 `POLICY_` / `CODEBOOK_`。

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `*_IMPORT_MAX_BYTES` | 20MB | 文件内容上限。网关另按 20MB+256KB 拒绝整个请求体。未带 Bearer 的上传不会先把文件写入服务。解压后不超过 64MB，最多 10 万行、128 列，同时最多两个解析 |
| `*_EXPORT_MAX_ROWS` | 100000 | 单次导出行数上限。导出是整表读进内存再生成 Excel，超限返回 422 并提示联系管理员 |

导出接受与列表完全相同的筛选参数，超限时先缩小筛选范围即可，不必直接调高上限。

## 爬虫监测数据源

只有同步 CLI 连爬虫库，服务进程不连；页面只读本服务库里聚合好的表。只读采集总表 `csys_policy_info_source_all`，
按「网站名称 + 省份 + 地市」的原始值统计（不做别名归一，只有空省份记作「国央企」、「国家」记作「全国」）；停更天数按最新入库日期计算。

| 变量 | 说明 |
| --- | --- |
| `POLICY_CRAWLER_MYSQL_HOST` / `_PORT` / `_USER` / `_PASSWORD` / `_DB` | 爬虫库连接，建议单独建**只读账号**，不要用 root |
| `POLICY_CRAWLER_HEALTH_NORMAL_DAYS` / `_WATCH_DAYS` | 状态分档阈值，默认 7 / 30。停更 ≤7 天正常，≤30 天关注，其余停更 |

服务器上用 [部署与维护](部署与维护.md) 里的 `$DC` 执行（`make crawler-*` 依赖本机 Compose，只在隔离环境用）：

```bash
$DC exec -T policy-service .venv/bin/python -m app.cli.sync_crawler --backfill                   # 首次：从总表最早采集日回填到今天，并建立水位（约 45 分钟）
$DC exec -T policy-service .venv/bin/python -m app.cli.sync_crawler --backfill --skip-existing   # 回填中断后续跑，沿用中断批次的水位
$DC exec -T policy-service .venv/bin/python -m app.cli.sync_crawler                              # 日常：按入库时间水位增量重算受影响的采集日
$DC exec -T policy-service .venv/bin/python -m app.cli.sync_crawler --days 30                    # 修复：固定重算，不动水位
```

已接入系统管理 → 任务调度，独立 `policy-worker` 每天执行增量同步，默认北京时间 10:10，可在页面调整。不要再配置重复的宿主机 cron。详见 [任务调度](任务调度.md)。

- 没有成功回填过时，日常同步会直接报错提示先回填，不会用短窗口算出偏小的数据总量。
- 新环境如果是整库迁移 `policy_db` 过去的（含 `policy_crawler_sync_runs` 里的水位），**不需要再回填**：
  确认能连上同一个爬虫库后直接执行日常同步，会从库里的水位接着把迁移期间新入库的数据补上。
  只有空库部署才需要回填。
- 已删除数据（`status='-1'`）不计入。爬虫方把旧数据标记删除不会改 `create_time`，日常增量感知不到，
  需要时用 `--days` 做一次修复性重算。
- 同步进程被杀或容器重启时，页面会提示「同步意外中断」，重新执行同步即可。
- 源端瞬时连接故障最多尝试三次，重试前重新连接；认证和 SQL 错误不重试。所有自然日计算使用北京时间，
  MySQL 无时区入库时间按北京时间解释，水位以 UTC 存储。

## AI提问

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `AI_ARK_API_KEY` | 空 | 字节方舟密钥。为空时方舟的模型在页面上显示「未配置密钥」 |
| `AI_BAIDU_API_KEY` | 空 | 百度千帆密钥，同上 |
| `AI_BATCH_CONCURRENCY` | 20 | 单个批量任务的并发请求数。频繁限流就调小 |
| `AI_BATCH_MAX_RUNNING` | 3 | worker 同时运行的任务数，多出来的排队 |
| `AI_BATCH_STALE_SECONDS` | 90 | 运行中的任务超过这么久没有心跳，判定为中断 |
| `AI_UPLOAD_MAX_BYTES` | 20MB | 模板 Excel、码表的上传上限，不能超过网关的请求体上限 |
| `CODEBOOK_AI_CALLER_SECRET` | 开发值 | 模板引用系统码表时，ai-service 调码表服务内部接口的密钥。compose 把它同时传给两边（码表服务拼成允许调用方表，ai-service 当调用密钥），只配这一个变量。生产环境必须换掉 |

可选模型、接入点、请求参数和单价不走环境变量，存在 `ai_models` 表，在「模型配置」页维护，保存即生效。

`ai-service` 和 `ai-worker` 都要出站访问方舟、千帆，所以和 `policy-worker` 一样接在 gateway 网络上；不发布端口。
新增 ai-service 时，服务器 `.env` 的 `IAM_INTERNAL_CALLER_SECRETS`、`AUDIT_INTERNAL_CALLER_SECRETS` 要加上 `ai-service`，
否则鉴权和审计投递都会失败。

## 政策 AI 打标

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `POLICY_POLICY_SOURCE_DB` | `bid_analyse` | 源政策所在库，和爬虫库同一个 MySQL 实例、同一套账号（`POLICY_CRAWLER_MYSQL_*`） |
| `AI_POLICY_CALLER_SECRET` | 开发值 | 政策服务调 ai-service 内部接口的密钥，compose 同时传给两边。生产必须换 |
| `CODEBOOK_POLICY_CALLER_SECRET` | 开发值 | 政策服务调码表服务内部接口（核对政策类型）的密钥，同上 |

三个打标任务（类型判断、政策解读、市场机会）各自的模板、每批条数、正文长度（全文或截取字数）、每日费用上限，以及类型判断的读取进度，
不走环境变量，存在 `policy_ai_tasks`（一任务一行），在任务调度页每个任务的「设置」里维护。

## 隔离验收栈

`deploy/compose/p6.env.example` → `deploy/compose/.p6.env`。库名必须是 `*_p6_db`，避免备份/恢复误伤开发库。

内部 JSON 密钥在 Compose 里写成 YAML 单引号字面量。不要写 `${VAR:-{"k":"v"}}`：Compose 会把第一个 `}` 当成插值结束，容器里只剩 `{`，服务无法启动。

## 容器启动

容器启动直接运行镜像构建阶段已安装的 `.venv/bin/uvicorn`；迁移和同步使用 `.venv/bin/alembic` / `.venv/bin/python`，不在运行时重新联网解析或安装依赖。
