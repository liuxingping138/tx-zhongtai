# 业务表主键与导入导出分析

记录日期：2026-09-20。范围：政策、码表模块的六张业务表，不包含系统管理表。

## 1. 当前决定：维持现状，等待业务口径

业务尚未明确各表的数据粒度、唯一性及覆盖规则，因此暂时保留当前数据库结构和导入导出行为。本文用于记录现状、限制和候选方案；建议部分不是已确定的业务规则，也不是已实现的功能。

本次仅整理文档，不修改表结构、约束、接口、页面或现有数据；不执行数据合并、清空或全量覆盖。业务给出最终口径后，再统一设计迁移、接口、Excel 模板和页面交互。

核查依据：前次已只读核对运行中数据库的主键和唯一约束，本次再次核对仓库中的模型与导入实现。本文不是对数据质量或业务规则正确性的验收结论。

## 2. 当前主键和上传行为

六张表的数据库主键均为自动生成的 UUID `id`。导入判断重复主要使用业务字段或内容哈希，而不是数据库主键。

| 业务表 | 数据库表名 | 唯一约束／导入匹配依据 | 当前上传行为 |
| --- | --- | --- | --- |
| 信源管理 | `policy_sources` | `internal_id`、`site_code` 分别唯一 | 仅新增；发现重复或业务校验错误时整批拒绝，不更新已有记录 |
| 政策基础标签 | `policy_base_tags` | 16 个业务字段计算的 `content_hash` 唯一 | 仅新增；发现重复或业务校验错误时整批拒绝 |
| 政策解读 | `policy_interpretations` | `relation_key` 唯一 | 关联键重复的行跳过，其余合格行新增，不更新 |
| 政策类型码表 | `codebook_policy_types` | `type_name` 唯一 | 同名且内容有变化则更新，不存在则新增；内容相同则跳过 |
| 行业场景码表 | `codebook_scenarios` | 31 个业务字段计算的 `content_hash` 唯一 | 整行内容重复则跳过，否则新增，不更新 |
| 地区码表 | `codebook_area_codes` | `county_id` 唯一 | 区县编码已存在则跳过，否则新增，不更新 |

当前没有上传全量覆盖模式：不会清空旧表，也不会删除文件中未出现的数据库记录。信源的“清空表”是独立操作，不属于上传流程。地区导入函数虽然名为 `upsert_area_code_rows`，实际仍是新增或跳过。

### 2.1 信源管理

- `internal_id` 为“网站名称＋省份名称＋地市名称＋标签”直接拼接后计算的 MD5；导入时重新计算，不使用文件中的内部 ID。
- `site_code` 有值时使用上传值；为空时，按地区编码前缀和已有最大流水号生成。
- 网站名称必填；未提供网站编码时需要地区编码。内部 ID、网站编码与数据库或文件内记录冲突，均会阻止整批导入。
- 修改 URL、抓取优先级等后重新上传，并不能更新原记录，仍可能因唯一标识重复而整批拒绝。

### 2.2 政策基础标签

- 内容哈希覆盖全部 16 个业务字段，采用 SHA-256；不是按政策名称唯一。
- 政策名称及地区编码存在相应校验。重复内容或校验错误会阻止整批导入。
- 修改备注、标签、评分等会改变哈希；该行可能被识别成新记录，原记录继续保留。
- 若将全表导出后仅修改一行再上传，其他未修改行可能因重复导致整批拒绝。

### 2.3 政策解读

- `policy_uid` 优先使用上传值；为空时取政策标题的 MD5。
- `relation_key` 由“政策 UID＋行业场景编码＋机会类型”直接拼接生成，不使用文件中的关联键。
- `tenant_id` 目前不参与唯一约束；是否应按租户隔离业务唯一性，需要业务确认。
- 同一关联键下，即使摘要、补贴、市场机会等内容有变化，导入仍会跳过。
- `record_id` 当前生成 UUID 字符串；Excel 表头“自增或雪花算法”与实际生成方式不一致。真实数据库主键仍是 `id`。

### 2.4 政策类型码表

这是当前唯一真正支持 Excel 增量更新的表：

1. 按类型名称 `type_name` 查找记录。
2. 不存在则新增；已存在则比较序号、名称、定义。
3. 内容有变化时更新原记录，版本号加一，更新操作人和时间；无变化则跳过。

修改类型名称会被当成新增，不能据此识别原记录改名。空单元格或缺少序号、定义列会被解析为空字符串，可能清空已有字段，不是“仅更新非空值”。

### 2.5 行业场景码表

- `industry_scenario_code` 目前没有唯一约束，不能直接视为每行唯一标识。
- 一行同时包含行业、场景、客群和产品信息，实际业务粒度尚未确认。
- 修改任一业务字段会改变内容哈希，可能新增另一条记录，而不是更新原记录。

### 2.6 地区码表

- 区县编码 `county_id` 必填且唯一；已有编码对应的名称、别名、简称不会被上传更新。
- 行政区划调整、编码变更及历史编码保留方式尚未明确。

## 3. 当前 Excel 解析和下载规则

- 前端上传接受 `.xlsx`。后端只读第一个工作表，以第一个非空行为表头，按已识别的列名映射字段；未知列忽略，空行跳过，字段首尾空格清理。
- 当前没有严格要求所有模板列齐全；缺失列会解析为空值。不能将“缺少列”等同于“不更新该字段”。
- 信源、基础标签在前端上传流程中先尝试匹配地区编码，再交由对应服务校验导入。
- 信源、基础标签整批拒绝时，报告包含全部输入行及校验说明；其余四表的报告主要记录被跳过的行。
- 六张表下载均调用全表查询，不传页面筛选和分页条件，因此下载的是全表数据。
- 导出固定业务列，以及入库时间、入库人、更新时间、操作人；不导出数据库 `id`、版本号、内容哈希。信源、解读等表会导出自身业务标识。
- 页面手动编辑与 Excel 上传是不同路径：手动编辑按 `id` 定位并使用版本号校验；不能据此认为 Excel 已具有相同更新能力。

暂时使用时，应将上传理解为上述各表已有的导入方式。除政策类型外，不应将“下载、修改、重新上传”作为通用批量编辑流程；已有记录需要修改时优先使用页面编辑。下载文件也不能视为包含全部内部字段的数据库备份。

## 4. 候选调整方案（未实施，待业务确认）

### 4.1 区分记录身份与内容变化

保留 UUID `id` 作为数据库主键。稳定的业务编码用于外部数据匹配，内容哈希仅辅助判断内容变化。是否移除原有哈希唯一约束、如何处理重复记录，需要在唯一性口径确定后设计迁移，不能直接删除约束。

| 表 | 候选匹配方式 | 需要确认的前提 |
| --- | --- | --- |
| 信源 | 优先 `id`，外部文件可用稳定的 `site_code` | 一条信源代表网站、栏目还是抓取入口；编码能否稳定不变；现有内部 ID 是否被外部引用 |
| 基础标签 | 优先 `id`，考虑补充稳定的 `policy_uid`，供解读关联 | 一条记录是否代表一份政策；修订版、转载、联合发文是否独立记录 |
| 政策解读 | 优先 `id`；候选业务键为租户、政策 UID、行业场景编码、机会类型的组合 | 同一组合是否允许多份解读或历史版本；空租户代表什么 |
| 政策类型 | 优先 `id`；无 ID 时可按名称匹配 | 类型名称是否允许修改、同义名称是否合并；是否需要独立类型编码 |
| 行业场景 | 暂优先按 `id` 精确更新 | 一个行业场景是否对应多个客群、产品；是否需要独立关联表 |
| 地区码表 | 优先 `id`；外部文件按 `county_id` 匹配 | 是否保存行政区划历史、失效编码和生效日期 |

名称、标题、描述、标签等会变化的字段不宜直接决定记录身份。基础标签的标题、部门、日期、原文链接可用于提示疑似重复，但未经确认不能自动合并。组合业务键宜采用数据库多列唯一约束，避免无分隔字符串拼接造成歧义。

### 4.2 统一导入模式与字段语义

候选模式：新增并更新、仅新增、仅更新。若业务认可，可将“新增并更新”作为默认模式。

- 有 ID 时按 ID 定位并校验权限；ID 不存在或无权限则报错，不自动降级为新增。
- 无 ID 时仅对具有可靠业务键的表自动匹配；匹配不唯一或缺乏依据时列为待确认，不按相似标题覆盖。
- 同一文件多行指向同一记录时提示冲突，不采用隐式“最后一行覆盖”。
- 候选空值规则：缺列不修改；更新行空单元格默认保留原值；清空操作在预览中显式指定。新增行仍需验证必填项。
- 内容完全相同计入“无变化”，不作为整批失败原因。
- 文件未出现的旧记录保留，不自动删除。

### 4.3 导入预览、并发保护与追溯

- 上传后先展示新增、更新、无变化、错误及冲突数量，可查看每个字段的修改前后值。
- 用户确认后提交；提交时重新检查版本、权限和唯一约束，不能仅依赖预览时的判断。
- 候选默认策略：存在错误先修正，提交整批成功或整批回滚。是否允许部分成功需业务确认。
- 保留导入批次、操作人、模板版本和修改前后值；若需要回滚，须另外设计对后续编辑及关联数据的保护，不能只凭日志直接覆盖恢复。

### 4.4 导出与全量同步

- 明确区分“导出当前筛选结果”和“导出全部数据”。
- 用于回传修改的 Excel 携带系统填写的记录 ID、版本号；新增行可以留空，日常新增、编辑表单无需人工填写这些自动字段。
- 提供独立新增模板，标注必填、编码格式、空值语义及模板版本。
- 暂不建议开放“清空再导入”。如业务需要全量同步，应明确同步范围、关联影响、缺失记录处理方式、变更预览、备份和恢复方案，单独设计。

## 5. 待业务确认清单

以下均为待确认项，目前没有默认视为已批准的答案。

| 编号 | 业务需要明确的问题 | 影响范围 |
| --- | --- | --- |
| B01 | 六张表分别以什么代表“同一条记录”？哪些字段允许改名或改编码？ | 业务唯一键、更新匹配 |
| B02 | 政策基础标签与解读如何关联？政策修订、同名政策、转载如何区分？ | 政策 UID、关联和历史版本 |
| B03 | 行业场景的一行代表什么？同一编码下多个客群、产品是否合法？ | 行业场景去重、是否拆表 |
| B04 | 政策解读是否按租户隔离？同一组合是否允许多条或多个版本？ | 组合唯一约束、权限和匹配 |
| B05 | 外部数据是否有可信且稳定的编码？上传以系统数据还是文件数据为准？ | 无 ID 文件处理、冲突策略 |
| B06 | 缺列、空单元格分别表示保留还是清空？是否允许部分成功？ | 更新语义、事务边界 |
| B07 | 是否需要全量同步？文件缺少的记录应保留、停用还是删除？ | 删除、关联和恢复策略 |
| B08 | 地区编码变化、历史政策和历史解读是否需要保留版本？ | 历史数据模型 |
| B09 | 是否接受回传模板携带记录 ID、版本号？旧模板如何兼容？ | Excel 模板与并发保护 |
| B10 | 现有重复或冲突数据由谁判定、如何合并，关联如何保留？ | 存量数据迁移 |

最终口径应补充确认人、确认日期、业务例子及验收样例，再更新本文状态。

## 6. 口径明确后的实施顺序

1. 确定各表的数据粒度和唯一键，准备新增、更新、同名、重复、空值等样例。
2. 只读检查存量数据与新规则的冲突，形成可审核的处理清单；准备备份与迁移恢复方案。
3. 统一调整模型约束、数据迁移、接口、导入导出模板和页面提示，兼顾现有外部标识及关联。
4. 实现预览、版本冲突校验、批次追溯及明确的失败处理。
5. 按业务样例验证导出回传、重复上传、字段清空、并发编辑和失败回滚后，再启用新规则。

上述步骤仅记录后续建议，不构成本次执行任务。
