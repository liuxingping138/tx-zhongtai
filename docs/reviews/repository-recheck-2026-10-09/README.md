## 尚需修复的问题

### R01 · P1 · F02 的 Excel 资源保护没有覆盖地区解析

`services/codebook-service/app/application/area_resolve.py:45` 的 `read_raw_sheet` 直接 `load_workbook`，没有公共解析器的解压大小、行数、列数限制，也没有关闭 workbook。`area_codes.py:233` 仍直接 `asyncio.to_thread`，绕开同时两次解析的限制。HTTP `/api/v1/codebook/area-codes/resolve` 实际调用此分支，上传压缩大小限制不等于解压/CPU/内存限制。

复现：含 129 列的有效 XLSX 被 `read_raw_sheet` 正常接受。修复应让此分支复用同一资源预算，并补实际 resolve 路径回归。

### R02 · P2 · F02 的处理行数限制可被稀疏工作表绕过

`packages/platform-common/platform_common/excel.py:95–111` 在空行 `continue` 后才按 `len(items)` 计数，限制的是非空结果条数，并非实际迭代的工作表行数。小体积文件可通过很远的行坐标让 openpyxl 产生大量空行，解压大小限制不能解决这种 CPU 消耗。

复现：表头在首行、唯一数据在第 100003 行，默认 100000 限制下仍成功返回。需要在迭代前核对尺寸，并对实际遍历的行列数设置预算，覆盖虚假/缺失尺寸以及稀疏行测试。

### R03 · P2 · 新上传解析器异常路径没有显式关闭临时文件

`packages/platform-common/platform_common/http_utils.py:113–125` 的流量检查抛 `ApiError`，直接从 parser 异常退出，未清理 parser 已创建文件；正常解析也只关闭选中的 `file`，允许的第二个文件、缺少 `file` 字段路径没有统一关闭 FormData。

复现：先上传约 1.1MiB 让临时文件落盘，再超出请求预算，返回 413 后捕获的文件对象 `closed=False`。最终 GC 可能释放，不能宣称必然永久泄漏，但请求退出时缺少确定性清理。应确保成功、超限、缺字段、多文件和取消等路径统一清理，补关闭断言。

### R04 · P1（发布前）· HTTPS 端口配置仍需统一

`deploy/compose/docker-compose.https.yml:11` 允许改变宿主机 `GATEWAY_HTTPS_PORT`，但 `deploy/gateway/traefik.https.yml:10–13` 通过固定 8443 的 websecure 入口生成 HTTP 跳转。只改宿主机映射会继续跳到 8443，而不是选定的新端口。此前服务器预检曾观察到其他服务占用 8443；本次 SSH 认证失败，不能确认其当前状态。

应先核实可用端口，将公网 HTTPS 端口、跳转目标、操作文档保持一致，实际验证 Location、证书、登录/刷新和自动续期后再判定 F04/D06 完成。Compose 语法有效并不代表路由和端口在目标服务器可用。

### R05 · P2 · D07 只新增备份入口，没有完成备份保障流程

`backup_business.sh` 提供了四库只读导出，但现行手册仍没有具体保留策略、异机存储配置/操作、恢复点与恢复时间目标、整库恢复演练证据。`test_restore_owner.sh` 只建表/序列再改 owner 并执行 ALTER，并未执行 pg_dump/pg_restore 或真实后续 Alembic 迁移。不能把这项简单属主测试当作 F10/D07 的整体验收。
